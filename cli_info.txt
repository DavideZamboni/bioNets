================================================================================
0   CLI
================================================================================
Python package that runs a four-stage scientific pipeline w command-line interface on top of it.
user types `mypsns ...`
in their terminal, the CLI reads its arguments, validates them, prints
pretty status messages, and calls into your existing services/ modules.

Settings can come from a YAML file, the command line, or both (command line wins on overlap). 

When a stage finishes, the CLI dumps the exact settings it used back to disk so you can reproduce the run later.

================================================================================
1   THE FOUR LIBRARIES
================================================================================

------------------------------------------
TYPER  --  turns Python functions into commands
------------------------------------------

Suppose you have this normal function:

    def greet(name, loud):
        print(f"hello {name}")

If you decorate it with Typer:

    import typer
    app = typer.Typer()

    @app.command()
    def greet(name: str, loud: bool = False):
        print(f"hello {name}")

then run `app()`, you can now do in the terminal:

    $ mytool greet --name Bob --loud

Typer reads the function's parameter names and types and builds the CLI
from them. No manual argument parsing. No argparse boilerplate. The
function body is what runs when the command is invoked.

Three Typer pieces show up in our code:

  typer.Typer()
      creates an "app" object that owns commands.

  @app.command()
      a decorator: "register this function as a command on the app."

  typer.Option(default, "--flag-name", "-f", help="...")
      attached to a function parameter. Says "this parameter is a CLI
      option (a --flag), not a positional argument; here's its default
      and its help text." A typical declaration:

          verbose: bool = typer.Option(False, "--verbose", "-v",
                                       help="Talk more.")

      Reads as: "the verbose parameter is a bool, defaults to False, and
      shows up on the CLI as both --verbose and -v."

  rich_help_panel="Some Group"
      An extra Typer feature we use heavily. When you pass this to
      typer.Option, the option gets grouped under "Some Group" in the
      --help output. So contacts has Parallelization / Trajectory window /
      Selectors / Geometric cutoffs / Behaviour sections, instead of one
      flat wall of fifteen flags.

  app.callback()
      A function that runs BEFORE any subcommand. We use it once, in
      cli.py, to read the global flags (-v, -q, --log-file) and configure
      logging before the user's chosen subcommand actually runs.

------------------------------------------
RICH  --  prints pretty things in the terminal
------------------------------------------

Normal Python:        print("error: bad file")  -- plain text
With Rich:            console.print("[bold red]error:[/bold red] bad file")
                      -- "error:" appears bold red in the terminal.

Rich pieces we use:

  Console
      An object that prints with colors and formatting. We make exactly
      one of these and share it (a "singleton"). Lives in logging_utils.

  Panel
      Draws a box around text. We use it for stage banners --
      "Stage 2/4 -- topology" shown inside a cyan box.

  Table
      Pretty ASCII table with column styling. We use it for inputs
      summaries ("here's what we'll run with") and report tables.

  RichHandler
      A Python logging handler. When you do `logging.info("hello")`,
      it gets routed through Rich and shows up with colors and a
      timestamp. Drop-in replacement for the stdlib StreamHandler.

You never call Rich directly inside the command files. You call the
helpers in logging_utils.py (print_banner, print_summary, print_error,
print_warning, print_success, print_info, print_kv_table). Those helpers
wrap Rich.

------------------------------------------
PYDANTIC  --  data classes that check themselves
------------------------------------------

Normal Python class:

    class ContactsConfig:
        def __init__(self, nc, d_a_dist):
            self.nc = nc
            self.d_a_dist = d_a_dist

If someone passes nc="banana", Python won't complain until that value is
used somewhere weird, much later, in a confusing way.

Pydantic version:

    from pydantic import BaseModel, Field

    class ContactsConfig(BaseModel):
        nc: int       = Field(default=2,   ge=1)
        d_a_dist: float = Field(default=4.5, gt=0)

Now `ContactsConfig(nc="banana")` fails IMMEDIATELY with:
"nc: Input should be a valid integer". The `ge=1` means "greater than or
equal to 1." `gt=0` means "strictly greater than 0."

Other Pydantic things we use:

  model_config = ConfigDict(extra="forbid")
      "If the YAML I'm loaded from contains a key I don't recognise,
      raise an error." Catches typos like `nonbouned_name` immediately.

  Field(default=..., description="...", ge=..., gt=..., le=..., lt=...)
      Field-level config: defaults, descriptions, numeric bounds.

  Literal["a", "b"]   (from typing)
      "Only these exact string values are allowed."
      So `targets: List[Literal["HBonds", "Salt_bridges", "HCs"]]` means
      a list where every entry must be one of those three exact strings.

  @field_validator("foo", mode="before")
      "Run this method to clean field 'foo' before Pydantic does its
      type check." We use it to convert raw strings into pathlib.Path
      automatically and expand `~` to the home directory.

  cfg.model_dump(mode="json")
      "Give me a dict version of this model, suitable for writing to
      YAML or JSON." Used in save_pipeline_config to produce
      run_config.yaml.

  ValidationError
      Raised by Pydantic when something fails. We catch it and repackage
      it as our own ConfigError so the CLI can show a friendly message.

------------------------------------------
PYYAML  --  reads and writes YAML files
------------------------------------------

YAML is a human-friendly config format. Indentation matters. Lists are
written with dashes:

    topology: protein.pdb
    contacts:
      nc: 8
      targets:
        - HBonds
        - Salt_bridges

PyYAML has two functions we care about:

  yaml.safe_load(file_handle)
      Read YAML -> Python dict.

  yaml.safe_dump(data, file_handle, default_flow_style=False, sort_keys=False)
      Write Python dict -> YAML.
      default_flow_style=False keeps the nested-indented format above
      (otherwise it tries to use {curly: braces}).
      sort_keys=False preserves insertion order.

The "safe" prefix means "do not execute arbitrary Python embedded in the
YAML." Always use the safe variants. The unsafe ones can execute code
hidden in a YAML file -- a security risk.


================================================================================
2   PYTHON CONCEPTS USED EVERYWHERE BELOW
================================================================================

DECORATOR
    A function that wraps another function. Written as @decorator on the
    line above the function definition. `@app.command()` means "register
    this function with the Typer app." `@field_validator("foo")` means
    "use this method to clean field 'foo' on a Pydantic model."

TYPE HINT
    The `: type` after a parameter name. `name: str` means "name is a
    string." Typer and Pydantic both READ these hints to figure out what
    kind of data they're dealing with -- they're not just documentation.

OPTIONAL[X]
    From the typing module. Means "either X or None." `Optional[Path] = None`
    means "defaults to None, but if set must be a Path."

LIST[X]
    "A list whose elements are of type X." `List[str]` is a list of strings.

LITERAL["a", "b"]
    "Must be exactly one of these specific values."

PATHLIB.PATH
    A modern way to represent a filesystem path. Better than raw strings
    because methods like `.exists()`, `.parent`, `.mkdir(parents=True,
    exist_ok=True)`, `.glob("*.csv")` come for free. We use this everywhere
    a path is involved.

DUNDER (DOUBLE UNDERSCORE)
    Names like __init__, __version__. Python convention for "special" names.
    __init__.py marks a folder as a Python package.

TYPER.EXIT(code=N)
    The polite way for a Typer command to stop. Code 0 = success, anything
    else = error. The CLI catches this and exits the process with that code.


================================================================================
3   cli.py  --  THE FRONT DOOR
================================================================================

mypsns run --config /home/davide/storage/lab_dati/psns_out/rec_grk_config.yaml --log-file results/run.log


WHAT IT IS
    The single entry point of the whole CLI. When someone types `mypsns ...`,
    Python starts here.

WHAT IT DOES, TOP TO BOTTOM

    Imports.
        Pulls in typer, our logging helpers, and the seven command modules.

    Defines __version__ = "0.1.0".
        Used by --version and printed by the version callback.

    Defines HELP.
        The big help text shown at `mypsns --help`. The [bold cyan]...[/bold
        cyan] tags are Rich markup; they render as colour because of the
        next step.

    Builds the Typer app:

        app = typer.Typer(
            name="mypsns",
            help=HELP,
            rich_markup_mode="rich",
            no_args_is_help=True,
            pretty_exceptions_show_locals=False,
            add_completion=False,
        )

      What each option means:
        name=                      shows up as the command in --help.
        help=                      the long description.
        rich_markup_mode="rich"    "interpret [tags] in help text."
        no_args_is_help=True       if user types just `mypsns`, show
                                   --help instead of crashing.
        pretty_exceptions_show_locals=False
                                   if something crashes, don't dump every
                                   local variable to the screen -- they can
                                   contain paths, data, secrets.
        add_completion=False       skip the shell-completion subcommand
                                   (we don't ship completion files).

    _version_cb(value).
        A "callback" that Typer runs when it sees --version. If value is
        True, print the version and call typer.Exit() to stop processing.
        is_eager=True (on the option below) means "run me before checking
        any required arguments" so `mypsns --version` works without
        needing a subcommand.

    main_callback (decorated with @app.callback()).
        Special. Typer runs this BEFORE any subcommand. We use it to
        call setup_logging() with the global verbosity flags. So by the
        time your `mypsns run ...` body executes, logging is already
        configured.

    Subcommand registration. Seven lines like:

        app.command(name="run", help="...")(run_cmd.run_pipeline)

      This is the same as putting @app.command() on top of the function
      definition, just called manually. We do it manually because each
      command's function lives in a separate file in commands/.

    main() function.
        Just calls app(). This is the function pyproject.toml's
        [project.scripts] points to, so typing `mypsns` in the terminal
        ends up calling main(), which calls app(), which dispatches.

WHY IT'S SO SHORT
    Separation of concerns. cli.py does only registration. Command logic
    lives in commands/*.py. Settings logic lives in config.py. Printing
    lives in logging_utils.py. Adding a new subcommand means adding one
    file in commands/ and one line in cli.py -- nothing else.


================================================================================
4   config.py  --  THE RULE BOOK FOR SETTINGS
================================================================================

WHAT IT IS
    The single source of truth for what parameters the pipeline accepts,
    what their types are, what their defaults are, and what constraints
    apply. Any invalid value (negative count, unknown choice, missing
    required field) is caught HERE, before any pipeline code runs.

THE TOP-LEVEL CONSTANT

    DEFAULT_NA_VALUES
        A list of strings that pandas treats as "missing data" when
        reading CSVs. The standard pandas list includes "NA" -- which
        is a problem because the topology has sodium atoms named "NA".
        We exclude "NA" from the default. (This is the same bug you've
        seen come up before; centralising it here means every CSV read
        in the pipeline uses the corrected list.)

THE FIVE PYDANTIC MODELS

    FFReaderConfig
        nonbonded_name       which .itp file holds the nonbonded params
        additional_residues  merge extras from resources/ (default True)
        na_values            the list above

    TopologyConfig
        max_to_check         how many forcefield entries to consider per
                             residue. -1 means "all", sorted by name
                             similarity.
        verbose
        na_values

    InteractorsConfig
        modes                a list. Each entry must be one of
                             "q_interactors" or "named_interactors".
                             Anything else fails validation.
        max_DA_charge        HBond donor/acceptor charge cutoff
        min_H_charge
        DA_masses            list of int (rounded atomic masses)
        min_abs_charge       salt bridge
        max_abs_charge       hydrophobic cluster
        max_num_heavy_ats    must be >= 1
        min_bonds_to_charged must be >= 0
        verbose
        na_values

    ContactsConfig
        nc                   workers count, must be >= 1
        ram_thresh           10 to 99 inclusive
        nframes              >= 1
        beg_frm              >= 0
        end_frm              -1 = end of trajectory
        interactors_type     list of literals
        targets              list of literals (HBonds / Salt_bridges / HCs)
        subject_chains       optional list of strings
        surrounding_chains   optional list of strings
        d_a_dist             > 0
        angle                0 to 180
        sb_cutoff, hc_cutoff > 0

    PipelineConfig
        The top-level model. Path fields (topology, trajectory, forcefield,
        outpath, log_file) plus one instance of each of the four stage
        models above (as ff_reader, topology_recognition, interactors,
        contacts).

ABOUT extra="forbid"
    Every model has `model_config = ConfigDict(extra="forbid")`. This means:
    if the loaded YAML contains a key the model doesn't declare, Pydantic
    raises an error. Catches typos in config files immediately, rather
    than silently ignoring them.

ABOUT THE PATH COERCION

    @field_validator("topology", "trajectory", ..., mode="before")
    def _coerce_path(cls, v):
        if v is None or isinstance(v, Path):
            return v
        return Path(str(v)).expanduser()

    YAML returns plain strings for paths. This validator runs BEFORE
    Pydantic's normal type check (mode="before") and converts strings
    into pathlib.Path objects. `.expanduser()` turns `~/foo` into
    `/home/davide/foo`.

THE LOADER / MERGER FUNCTIONS

    load_yaml(path)
        Reads a YAML file and returns a dict. If the file doesn't exist
        or has bad syntax, raises ConfigError with a clear message.
        Verifies the top-level YAML is a dict (not a list or scalar).

    _deep_clean(d)
        Walks a nested dict and drops every key whose value is None.
        Why? The CLI uses None as "user didn't specify this flag." When
        merging CLI flags into a YAML-loaded dict, we must drop the
        Nones so they don't overwrite real config values.

    _deep_merge(base, override)
        Recursive dict merge. base = YAML. override = cleaned CLI flags.
        Override values win; nested dicts merge key-by-key (NOT replaced
        wholesale). So if YAML has

            contacts: {nc: 8, d_a_dist: 4.5}

        and CLI gives

            contacts: {nc: 16}

        you end up with

            contacts: {nc: 16, d_a_dist: 4.5}

        and NOT just `contacts: {nc: 16}`. This is the right behavior:
        a CLI override for one field should not erase the other fields
        in the same section.

    build_pipeline_config(config_path, overrides)
        The main entry point. Loads YAML, applies overrides, validates
        with Pydantic. If Pydantic complains, repackages the error as
        a friendly ConfigError listing each invalid field on its own
        line, so the CLI can show it instead of a tower of stack frames.

    save_pipeline_config(cfg, path)
        Dumps the resolved config back to YAML. Used for reproducibility:
        every successful stage writes a run_config.yaml to the output
        folder.

THE ConfigError CLASS
    A custom exception. The CLI catches it at command boundaries and
    prints a clean error. You never see a Python traceback for a
    config problem.


================================================================================
5   logging_utils.py  --  ALL THE PRETTY PRINTING
================================================================================

WHAT IT IS
    Owns the Rich console and provides a small set of pretty-print
    helpers. Command modules NEVER touch Rich directly. They call
    helpers here. That way, restyling everything is a one-file edit.

GET_CONSOLE
    Returns the singleton Rich Console. "Singleton" = "exactly one
    instance, made once and reused." First call creates it; subsequent
    calls return the same object. Lives in module-level variable
    _console. Why a singleton: Rich state (theme, output stream) should
    be consistent across the whole CLI; if every helper made its own
    Console, banners and tables could end up looking inconsistent.

SETUP_LOGGING
    Configures Python's standard logging module.

    Inputs:
      verbosity (int)   0 = INFO (default), 1 = INFO with caller paths,
                        2 = DEBUG
      quiet (bool)      overrides verbosity; only WARNING and above
                        on stdout
      log_file (Path)   optional file to receive a DEBUG-level log

    What it does:
      1. Wipes any existing log handlers (so re-running setup is safe).
      2. Adds a RichHandler -- routes log records through Rich for
         colour and timestamps.
      3. If log_file is given, adds a FileHandler at DEBUG level with a
         plain text format. The file gets the full firehose even if the
         console is set to WARNING.
      4. Sets the root logger level to the lower of (console level,
         DEBUG-if-log-file). The level controls what reaches handlers.

PRINT_BANNER(title, subtitle)
    Prints a cyan Panel (a box) with bold cyan title and optional dim
    subtitle. Used at the top of every stage so you can scroll back
    through logs and find stage boundaries quickly.

PRINT_SUMMARY(title, data)
    Prints a two-column Table: parameter name | value. Used for "here
    are the inputs / settings I'll run with." Uses _fmt_value internally
    to format values consistently:
      - lists -> joined with ", "
      - None  -> "auto" in dim style
      - True  -> green "on"; False -> dim "off"

PRINT_KV_TABLE(title, rows)
    Three-column variant: check name | status icon | detail. Used by
    `validate` for "topology loadable: ✓: 42352 atoms".

PRINT_ENV_INFO
    Logs a small banner with environment info: timestamp, Python
    version, OS, architecture. Useful for reproducibility -- if a run
    breaks six months later you can compare environments.

PRINT_ERROR / PRINT_WARNING / PRINT_SUCCESS / PRINT_INFO
    One-line status messages with a coloured prefix glyph:
      ✗ Error    (bold red)
      ⚠ Warning  (bold yellow)
      ✓          (bold green)
      →          (cyan)
    Consistent visual vocabulary across every command.

================================================================================
7   commands/_helpers.py
================================================================================

WHAT IT IS
    Shared utilities used by every command module. The leading underscore
    in the filename is convention: "don't import this from outside the
    commands/ package; it's internal."

THE HELPERS, ONE BY ONE

    collect_overrides(values, stage_key=None)
        Takes a dict of {option_name: option_value} and turns it into
        a nested override dict suitable for build_pipeline_config().

        Step 1: drop everything whose value is None (user didn't set).
        Step 2: split into "top-level" keys (topology, trajectory,
                forcefield, outpath, log_file) and "stage-level" keys
                (everything else).
        Step 3: nest the stage-level keys under stage_key.

        Example. Called with:
            values = {
                "topology":      Path("p.pdb"),
                "outpath":       Path("out/"),
                "nc":            None,
                "ram_thresh":    80,
            }
            stage_key = "contacts"
        Returns:
            {
                "topology":   Path("p.pdb"),
                "outpath":    Path("out/"),
                "contacts":   {"ram_thresh": 80},
            }
        which is exactly the shape build_pipeline_config wants.

    load_or_die(config_path, overrides)
        Wraps build_pipeline_config. On success, returns the
        PipelineConfig. On ConfigError, prints the error via the Rich
        helpers and calls typer.Exit(code=2). The CLI exits cleanly
        without a Python traceback. "die" in the name is the classic
        Perl idiom for "fail loudly but cleanly."

    ensure_dir(path)
        Creates a directory and any missing parents. Doesn't complain
        if it already exists. One-liner around path.mkdir(parents=True,
        exist_ok=True). We have it as a helper so the same idiom is
        used everywhere.

    dump_run_config(cfg, outpath)
        Saves the resolved config to <outpath>/run_config.yaml. Called
        after every successful stage so the run is reproducible. The
        same config dump-back also captures CLI overrides that weren't
        in the original YAML, so the file is a true snapshot.

    stage_done(marker)
        Returns True if the given file/folder exists. Used by --resume
        logic in each command.

    ff_outdir_name(ff_folder)
        Mirrors the parser_dispatcher naming convention: takes a path
        like /forcefields/amber99sb.ff and returns "amber99sb"
        (strips ".ff" suffix, "ff." prefix, replaces "-" with "_").
        This is the folder name the ff_reader stage writes its outputs
        into; we need to reproduce it elsewhere to find those outputs.

    show_paths(cfg)
        Prints a quick paths summary using print_summary. Available so
        we don't repeat the same dict literal in every command.

    require_path(label, p, must_exist=True)
        Validates that a path arg is present and (optionally) that it
        exists on disk. On failure: prints a clear error and exits
        with code 2. Returns the validated, expanded Path on success.

    warn_skip(marker, stage, overwrite)
        Returns True if (a) the marker exists and (b) overwrite is
        False. Prints a warning explaining the skip. Used by every
        stage to decide whether to re-run.


================================================================================
8   commands/ff_reader_cmd.py
================================================================================

WHAT IT IS
    Implements `mypsns ff-reader`. Parses a GROMACS forcefield folder
    (the .rtp/.tdb/.itp files) into the CSVs the rest of the pipeline
    consumes.

PANEL CONSTANTS AT TOP OF FILE
    PANEL_GENERAL, PANEL_FFOPTS, PANEL_BEHAVE. Strings used as the
    rich_help_panel argument when declaring options. Group flags under
    "General", "Forcefield options", "Behaviour" in the --help screen.

THE ff_reader FUNCTION

  Options (each appears as a CLI flag):
    --config              YAML config file
    --forcefield, -ff     forcefield folder
    --outpath, -o         output root
    --nonbonded-name      override the default .itp filename
    --no-additional-residues   skip the resources/ merge
    --overwrite           force recomputation
    --dry-run             validate & print plan, don't run

  Note on --no-additional-residues. It's a bool flag, defaults to False.
  We special-case it in collect_overrides:

      "additional_residues": (False if no_additional_residues else None)

  meaning: if user passed --no-additional-residues, set
  additional_residues=False; otherwise leave it None so it doesn't
  override the YAML value.

  Flow:
    1. Build an overrides dict via collect_overrides with stage_key
       "ff_reader".
    2. Load + validate the config via load_or_die.
    3. Validate the forcefield folder exists and outpath is set.
    4. Compute the output subfolder name (ff_outdir_name).
    5. Print banner + inputs summary.
    6. If --dry-run, exit here.
    7. Check the marker file (final_ff_residues.csv). If present and
       --overwrite NOT given, warn and exit.
    8. Import the service module (`from ..services.ff_reader import
       FFReader`). Catch ImportError and exit with code 3 if the
       service isn't there.
    9. Call FFReader(...).run().
    10. On any exception, log the full traceback to file (via
        log.exception) and print a one-line error to console.
    11. On success: dump run_config.yaml and print a green success line.


================================================================================
9   commands/topology_cmd.py
================================================================================

WHAT IT IS
    Implements `mypsns topology`. Matches each residue in the user's
    topology against the parsed forcefield, producing CSVs in
    <outpath>/Topology_recognition/.

OPTIONS
    --config, --topology/-t, --forcefield/-ff, --outpath/-o,
    --max-to-check, --verbose-stage, --resume, --overwrite, --dry-run

FLOW
    Same general shape as ff-reader: collect overrides, load config,
    validate paths (topology AND forcefield must exist), print summary,
    handle dry-run and overwrite, import service, call it, dump config.

ONE EXTRA STEP -- _resolve_ff_path
    The topology stage can take either the raw forcefield folder OR
    the parsed copy in <outpath>/<ff_name>/. It prefers the parsed
    copy when available, because reading the pre-parsed CSVs is much
    faster than re-parsing the .rtp/.tdb files.

CALL SITE
    Imports `Topology_recognition` from services. Constructs an
    instance with topology, outpath, ff_path, na_values, outlog.
    Then calls .get_restypes(verbose=...) and .get_ff_parameters(
    verbose=..., maxToCheck=...) in sequence. These match the methods
    on your existing class.


================================================================================
10   commands/interactors_cmd.py
================================================================================

WHAT IT IS
    Implements `mypsns interactors`. Tags every atom in the topology
    with its interaction roles (HBond donor/acceptor, salt-bridge,
    hydrophobic cluster, etc.) producing per-variant CSVs in
    <outpath>/Interactors/found_topologies/ plus residue_index.csv
    and atom_index_map.csv.

OPTION PANELS
    General, Modes, HBond tuning, Salt bridge tuning, Hydrophobic
    cluster tuning, Behaviour. Six visual sections in --help, so the
    twelve-ish flags don't run together.

KEY OPTIONS
    --mode, -m            repeatable. Choose q_interactors and/or
                          named_interactors. Repeat the flag for
                          multiple, e.g.
                              --mode q_interactors --mode named_interactors
    --max-da-charge, --min-h-charge       HBond tuning
    --min-abs-charge                      salt bridge tuning
    --max-abs-charge, --max-num-heavy-ats,
    --min-bonds-to-charged                hydrophobic cluster tuning

FLOW
    Same general shape. Extra check: the Topology_recognition folder
    must exist (the previous stage). If it doesn't, prints a friendly
    error pointing the user at `mypsns topology` and exits with
    code 2.

CALL SITE
    Imports Interactors. Constructs with topology, general_outpath,
    na_values, outlog. Calls .get_complete_topology(verbose=...) then
    .add_inttypes(verbose=..., max_DA_charge=..., min_H_charge=...,
    DA_masses=..., min_abs_charge=..., max_abs_charge=...,
    max_num_heavy_ats=..., min_bonds_to_charged=...). Matches the
    keyword arguments on the existing class.


================================================================================
11   commands/contacts_cmd.py
================================================================================

WHAT IT IS
    Implements `mypsns contacts`. Runs the actual MD trajectory
    analysis -- the expensive stage.

OPTION PANELS
    General, Parallelization, Trajectory window, Selectors, Geometric
    cutoffs, Behaviour. So the user can navigate the ~16 flags
    visually rather than reading a flat list.

KEY OPTIONS
    --nc                       worker count
    --ram-thresh, --nframes    HBond batching tuning
    --beg-frm, --end-frm       frame window
    --target                   repeatable: HBonds / Salt_bridges / HCs
    --interactors-type         repeatable
    --subject-chain            repeatable
    --surrounding-chain        repeatable
    --d-a-dist, --angle, --sb-cutoff, --hc-cutoff   geometric cutoffs

REPEATABLE OPTIONS
    Anything declared as `Optional[List[str]] = typer.Option(None, ...)`
    can be passed multiple times. Each occurrence adds one element
    to the list. So:
        --target HBonds --target Salt_bridges
    becomes targets = ["HBonds", "Salt_bridges"] in the config.

FLOW
    Builds an unusually large overrides dict (because contacts has the
    most settings), but otherwise follows the same pattern. Requires
    the Interactors folder to exist. Calls Contacts(topology,
    trajectory, general_outpath).run(**all_settings).


================================================================================
12   commands/run_cmd.py
================================================================================

WHAT IT IS
    Implements `mypsns run`. The full-pipeline orchestrator. Calls
    the four stages in sequence.

OPTIONS
    The basic path options (topology, trajectory, forcefield, outpath),
    a couple of common contacts overrides (--nc, --target) for
    convenience, and pipeline-control flags (--only, --skip, --resume,
    --overwrite, --dry-run).

    Why only a couple of contact overrides? Adding all of them at the
    top level would clutter --help. The intended pattern is: put the
    bulk of your settings in a YAML file, and use the run command's
    short option list for the most common quick overrides. Anything
    else: edit the YAML or use the per-stage subcommand.

THE STAGE FUNCTIONS
    _run_ff_reader, _run_topology, _run_interactors, _run_contacts.
    Each takes the same arguments (cfg, resume, overwrite) and does:
      1. Print a "Stage N/4 -- name" banner.
      2. Compute the marker path.
      3. If marker exists and (resume or not overwrite), skip with
         an info line.
      4. Otherwise import the service, call it, log success.

THE DISPATCHER (_run_stage)
    A small if/elif tree that routes a stage name to its function.
    Could be a dict, but with four stages the explicit form is fine.

THE STAGE SELECTION (_resolve_stage_set)
    Computes which stages to run.
      - --only X --only Y   ==> run only X and Y (in pipeline order)
      - --skip Z            ==> run everything except Z
      - default             ==> run all four

VALIDATION
    Before running:
      - all four canonical paths must be set / exist
      - if contacts is in the plan, trajectory must be set

REPRODUCIBILITY
    Before running anything (after dry-run check, after validation),
    dump run_config.yaml so even a partial run leaves a record.

ERROR HANDLING
    Each stage call is wrapped in try/except. typer.Exit from sub-stage
    is re-raised only if it has a non-zero code (success exits propagate
    but don't terminate the pipeline). Any other exception is logged
    with full traceback to file, but only a one-line summary appears
    on screen, and the run exits with code 1.

TIMING
    timeit.default_timer() at the start and end. Prints "Pipeline
    complete in 134.2s" at the bottom. Useful for cluster monitoring.


================================================================================
13   commands/validate_cmd.py
================================================================================

WHAT IT IS
    Implements `mypsns validate`. A pre-flight check command that
    validates a config without running anything expensive. Use this
    before submitting a long cluster job.

OPTIONS
    --config (required)        the YAML to validate
    --deep                     also try to load the topology/trajectory
                               through MDAnalysis and report counts

WHAT IT CHECKS
    1. Config schema valid (via build_pipeline_config).
    2. Each referenced path exists.
    3. The forcefield folder has at least one .rtp file plus the
       expected nonbonded .itp file.
    4. The output path is writable (writes and deletes a probe file).
    5. (with --deep) topology loads via MDAnalysis. Reports atom and
       residue counts.
    6. (with --deep) trajectory loads. Reports frame count.

OUTPUT
    A three-column Rich table: Check / Status / Detail.
    Each check returns a row with a ✓ (green) or ✗ (red) icon.
    If any check failed, exits with code 1.


================================================================================
14   commands/report_cmd.py
================================================================================

WHAT IT IS
    Implements `mypsns report <outpath>`. A post-run inspector that
    walks the output folder and tells you what's there.

OPTIONS
    Positional argument: outpath (a folder).
    --json    emit the report as JSON instead of pretty tables.

WHAT IT DOES
    For each pipeline stage, looks at the corresponding subfolder and
    decides whether it's complete:

      ff_reader            looks for any subfolder containing
                           final_ff_residues.csv. Reports the names.
      topology_recognition looks for complete_residue_topologies.csv;
                           if absent but unmatching_*.csv is present,
                           reports "stage ran but some residues
                           unmatched."
      interactors          looks for residue_index.csv and
                           atom_index_map.csv. If present, counts
                           variants in found_topologies/, residues in
                           residue_index.csv (line count minus header),
                           and atoms in atom_index_map.csv.
      contacts             looks for *_final.csv files (per-target
                           final tables), *_adjacency.dat files,
                           and persistency elbow CSVs.

OUTPUT MODES
    Default: prints a Rich table per section.
    --json:  emits the full payload via console.print_json. Pipe to
             `jq` for scripting.

================================================================================
17   WHAT HAPPENS WHEN THE USER TYPES `mypsns run --config foo.yaml`
================================================================================

Step-by-step trace through the code:

  1. The shell finds the `mypsns` entry point installed by pip. This is
     a tiny generated script that just imports mypsns.cli and calls main().

  2. main() in cli.py calls app(). Typer parses argv.

  3. Typer sees the global flags (--config is per-command, not global,
     so nothing for the global callback to do here beyond defaults).
     It runs main_callback() with verbose=0, quiet=False, log_file=None.
     main_callback calls setup_logging(0, False, None) -- so we get
     INFO-level Rich output on stdout.

  4. Typer recognises "run" as a registered command. It dispatches to
     run_cmd.run_pipeline.

  5. run_pipeline parses its own options. --config foo.yaml means
     config = Path("foo.yaml"). All other options are at their defaults
     (None for paths, False for bools, etc.).

  6. run_pipeline assembles its overrides dict. Since nothing else was
     passed on the CLI, overrides is empty (or close to it).

  7. load_or_die(config, overrides) calls build_pipeline_config.
     Inside:
        a. load_yaml(foo.yaml) -> dict.
        b. _deep_merge(yaml_dict, _deep_clean(overrides)) -> dict
           (effectively just yaml_dict since overrides is empty).
        c. PipelineConfig(**merged) -> validates with Pydantic.
        d. If validation passes: return the PipelineConfig.
        e. If validation fails: raise ConfigError with a friendly
           message. load_or_die catches it, prints a red error,
           exits code 2.

  8. require_path checks each path. If anything is missing or doesn't
     exist on disk: red error, exit code 2.

  9. _resolve_stage_set returns ["ff-reader", "topology", "interactors",
     "contacts"] (no --only or --skip given).

  10. print_env_info prints a small table with Python version, OS, etc.

  11. print_banner prints the "myPSNs run" banner.

  12. print_summary prints the plan table.

  13. ensure_dir creates outpath if needed.

  14. dump_run_config writes outpath/run_config.yaml.

  15. For each stage in [ff-reader, topology, interactors, contacts]:
       _run_stage dispatches.
       The stage function:
         - Prints "Stage N/4 -- name" banner.
         - Checks marker file. Skips if present (with info line) and
           --resume is set OR --overwrite is NOT set.
         - Imports the service module.
         - Calls the service.
         - Prints success line.
       On any exception: logs full traceback to file (if --log-file
       was given), prints a one-line error, exits code 1.

  16. After all stages: print "Pipeline complete in N.Ns" success line.

  17. Process exits with code 0.


================================================================================
18   "IF I WANT TO X, CHANGE Y" CHEAT SHEET
================================================================================

ADD A NEW CLI FLAG to an existing stage:
  1. Add the field to the corresponding Pydantic model in config.py
     (with default + description).
  2. Add a `typer.Option(None, "--my-flag", help="...")` parameter to
     the corresponding command function.
  3. Add it to the collect_overrides({...}) dict in that command.
  Done. Validation, YAML support, --help text all come for free.

ADD A NEW STAGE to the pipeline:
  1. Create the service module under mypsns/services/.
  2. Add a NewStageConfig Pydantic model in config.py.
  3. Add it to PipelineConfig.
  4. Create mypsns/commands/new_stage_cmd.py modelled on the others.
  5. Add it to commands/__init__.py.
  6. Register it in cli.py with app.command(...).
  7. (Optional) Add a _run_new_stage function and include it in
     _run_stage / _resolve_stage_set in run_cmd.py if it should be
     part of the full pipeline run.

CHANGE A DEFAULT VALUE:
  config.py. Find the Field(default=...) on the right Pydantic model.
  Edit. That's it -- everything that uses the config picks up the new
  default automatically.

CHANGE HELP-TEXT GROUPING in --help:
  Find the PANEL_* constants at the top of the command file. Change
  the rich_help_panel argument on the relevant options to put them in
  a different group.

CHANGE COLOURS or banner style:
  logging_utils.py. All Rich styling lives here. Edit print_banner,
  print_summary, the Rich markup strings, etc.

ADD A NEW VALIDATION CHECK to `mypsns validate`:
  commands/validate_cmd.py. Add a function that returns
  (label, status, detail), call it inside `validate()`, append the
  result to the rows list.

DEBUG A FAILING STAGE:
  Run with -vv (DEBUG-level logging) and --log-file. The on-screen
  output stays readable, but the log file gets the full traceback.

REPRODUCE A RUN someone else did:
  Take their run_config.yaml (in their outpath), and run
  `mypsns run --config their_run_config.yaml`. Same inputs, same
  outputs, same code path -- modulo upstream code changes.
